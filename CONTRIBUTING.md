# Разработка LeafDank

## Основная ветка
Исходный fork: `flex3r/DankChat`, ветка `develop`. Периодически сверяемся с upstream, но не вносим обновления вслепую. Для новых функций используем небольшие тематические изменения. Происхождение и лицензии не теряем.

## Перед каждой задачей
- Проверить состояние репозитория и точную версию инструментов.
- Найти существующее поведение в DankChat и сравнить с Leafyrino.
- Указать минимальный набор затронутых файлов, проверку и план отката.
- Если работа касается авторизации или недокументированных API, сначала написать исследовательский документ: права, риски, доступные методы и fallback.
- Все изменения удалённого репозитория требуют прямого разрешения владельца.

## Код
- Следовать существующей структуре и стилю Kotlin/Compose.
- Не создавать отдельные независимые движки чата для каждого UI.
- Не добавлять преждевременно Rust, JNI, вторую базу или второй сетевой стек.
- Внешние сервисы должны иметь интерфейс отказа без падения основного чата.
- Строки интерфейса локализуемые; ошибки не скрывать от пользователя.
- Не записывать OAuth-токены, cookies, headers с секретами и пользовательские сообщения в публичные логи.

## Проверки перед объединением
- Для любых изменений в UI: основной чат, скролл, быстрый поток сообщений, GIF, 7TV, история, вкладки и черновики.
- Для модификаций сети: разрыв, восстановление, rate limits, отмена запросов, устаревший OAuth.
- Выполнить применимые проверки Gradle (`testDebug`, `:app:spotlessCheck`, `:app:detektDebug`, `:app:lintDebug`, APK build) после проверки среды.
- Сопоставить память/скорость со стоковым DankChat там, где работа затрагивает производительность.
- Сообщить точные результаты; «не запускалось» не превращать в «прошло».

## Коммиты
`docs:`, `feat:`, `fix:`, `test:`, `refactor:`, `build:`, `chore:`.
Один коммит = одно осмысленное изменение. Не добавлять двоичные APK, ключи, output Gradle, дампы, токены и приватные данные.
